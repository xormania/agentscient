# LD-112

| field | value |
|---|---|
| observed | 2026-09-16 |
| where | ops/devlane/dispatch/launch.py, the codex launch; met live on A-87, record 20260916T142321Z-code-codex-285306 |
| defect | A dispatched worker cannot act in the coordination store. codex is launched `--sandbox workspace-write` with `sandbox_workspace_write.writable_roots=["<record>/out"]`, so every shell command it runs sees ~/.local/state/agentscient/state.db read-only. A-87's worker read its brief, ran `show A-87`, took generation 2 and issued the correct `coordination.py claim A-87 --branch lane/session-20260916-a87 --generation 2`; it exited 1 on `sqlite3.OperationalError: attempt to write a readonly database`. Claim, question and submit are all unreachable this way, so the coordination half of the trial could not run. The acting projection exists and would not be sandboxed - `ops/conductor/tools/coordination_mcp.py` carries coord_claim, coord_send and coord_submit, and codex spawns MCP servers as ordinary child processes outside the shell sandbox (lane_mcp.py ran as pid 1257391, a plain python3 child, and the store is writable by this uid) - but **the launch wires only `agentscient_lane` to lane_mcp.py**, whose eleven tools are lane_actions, lane_alerts, lane_brief, lane_changes, lane_findings, lane_handoffs, lane_homes, lane_jobs, lane_record, lane_start and lane_usage, with zero mentions of claim, submit or coordination. So the worker had no acting surface at all: the CLI was read-only and the server that could act was never wired in. |
| repair | Wire coordination_mcp.py into the codex launch beside agentscient_lane, so a dispatched worker acts through coord_claim, coord_send and coord_submit. A scope reworded to "act through the MCP tools, never coordination.py" is not sufficient on its own and would have failed the same way, because the tools were absent from the session. A writable store root in the launcher is the alternative, and is the weaker one: it hands a worker the whole store instead of a typed projection. |
