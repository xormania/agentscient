## What the audit does not cover

Written here as well as in the PR body because this is the thing a later
reader is most likely to get wrong. The audit was taken at `b1d868b0`.
`b902246d`, the `revoke` verb, is new surface it never saw: it came out
of the live run — the store holds two leads because `grant` appends and

## What went wrong, and what it cost

**Seven of my sixteen probe rows proved nothing until they were run.**
They anchored on a function's name and expected a string several lines
into its body; the docstrings between the two run ten lines, so each row
read a window that never reached the clause it asked about. First run:
PASS 359, FAIL 7 over 366 rows, all seven mine. They pass now because
each anchors on the line carrying its own clause. The lesson is not "run
the corpus" — it is that a row whose window is wide enough passes for a
reason unrelated to what it claims, and only the run can tell the two
apart.

**A pin can claim more than the thing it pins can deliver.** The ruling
asked for a case pinning that a read leaves the store's bytes unchanged.
Written literally, over every file whose name begins with the store's, it
failed: a read-only connection to a WAL database materialises
`state.db-shm`, and a zero-length `state.db-wal` when the writer has
checkpointed them away. Neither carries content. The pin is the database
file's bytes unchanged and the log carrying no frames, which is the claim
a read can actually be held to. The first version would have been a red
that never went green and a rule nobody could satisfy.

**Three test rows measured the wrong refusal.** A row expecting class
`revision` met class `evidence` because `reopen` hands its revision to
the engine as the move's evidence and the engine looked first; a row
about who may revoke ran a session its fixture had never bound and met
class `participant`, the earlier gate. Both are true refusals and neither
is the rule the row is about. A refusal class arriving from an earlier
gate is a row testing the fixture, not the behaviour.

**The wall caught a word I did not choose.** The read-only reader listed
the store's tables through SQLite's catalogue under its original name,
which contains the release branch's word, and the lane's literals verb
refused the tree in CI, not locally. `sqlite_schema` is the same
catalogue under the name SQLite 3.33 gave it. Pitfall 17's remedy —
spell the branch from `ops/lane.conf` — does not apply to a table name
that merely contains it, and reaching for the remedy without reading the
line would have produced nonsense.

**A citation was taken from the message that named it rather than the
record.** `73e47041` spells the Grok reader finding
`20260916T101838Z-review-grok-7bbe10#2`, taking the timestamp from the
Codex record beside it in the sentence I was reading. The record is
`20260916T101802Z`. The tree cannot be rewritten, so the correction lives
in the citation record and in the ledger.

## What worked

Reproducing the reviewers' findings from their own verbatim scripts out
of the ledger's `reproduce` column, rather than from paraphrases, before
ruling on any of them: fourteen of fifteen ran, and the one that did not
(Grok's bootstrap race, whose barrier sat inside a statement on the other
connection) was reported as not running rather than quietly restated.
Making the suite generation-agnostic as a separate green-on-its-own
refactor before the generation rule changed, so that nothing in the
refactor carried the new behaviour. And asking the Lead before writing
`revoke`, rather than after, about the two things only the Lead could
settle: whether it belonged in this PR at all, and whether the caller is
exempt from the last-lead rule. Both answers changed the code.
