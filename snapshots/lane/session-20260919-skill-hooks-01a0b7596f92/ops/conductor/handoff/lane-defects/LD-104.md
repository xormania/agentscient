| observed | 2026-09-16 |
| where | ops/devlane/dispatch/launch.py, `_lane_mcp` (`tool = Path(snapshot) / LANE_MCP_REL`, `ops/conductor/tools/lane_mcp.py`) |
| defect | Same shape as finding 1 of the #254 security-audit record `20260916T151749Z-review-codex-ef6db7`, fixed for the acting coordination server in `86a31c50` (PR #262): `_lane_mcp` sources the lane MCP server from a path inside the worker's own writable snapshot rather than the launcher's own tree, and any sibling-relative import inside `lane_mcp.py` that resolves by `sys.path[0]` would resolve from that same worker-writable directory. A worker that rewrote `ops/conductor/tools/lane_mcp.py` in its own snapshot before the server started would have the lane server run the worker's own code. This is pre-existing, predates the #254 PR, and is untouched by it — not folded into that fix's scope. Narrower blast radius than the acting server's: `LANE_MCP_TOOLS` (`lane_brief`, `lane_jobs`, `lane_changes`, `lane_findings`, `lane_record`, `lane_alerts`, `lane_usage`) are documented as reads, and no core mutation verb is reachable through it today — but the sourcing defect is identical in kind, and every dispatch wires this server, not only codex ones. |
| repair | Mirror the acting server's fix: add `LANE_MCP_PINNED = APP.parents[1] / "conductor" / "tools" / "lane_mcp.py"` beside `COORD_MCP_PINNED`, set `tool = LANE_MCP_PINNED` in `_lane_mcp`, and drop `LANE_MCP_REL` the way `COORD_MCP_REL` was dropped. Audit `lane_mcp.py`'s own imports for the same `sys.path[0]`-resolution risk `coordination_mcp.py` had, in case a future mutation makes it load a sibling module from the run directory. |
| tests | Planted fault mirroring `TheActingServerIsSourcedFromThePinnedTreeNotTheSnapshot` (`ops/devlane/dispatch/tests/test_launch_coordination_mcp.py`): plant a worker-owned `lane_mcp.py` in the snapshot before dispatch and assert the server argv is not sourced from the snapshot, and that the served file's content does not carry the planted marker. Clean neighbour: the existing `EachHarnessCarriesTheServer` suite in `test_launch_worker_mcp.py`, unaffected. |
