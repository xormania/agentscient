## Root cause, in the launcher

`ops/devlane/dispatch/launch.py`:

- Line 639: `COORD_MCP_HARNESSES = ("codex",)` — hardcoded, one harness.
- `_coordination_mcp()` (line 724): `if harness not in COORD_MCP_HARNESSES: return {"unresolved":
  f"the acting server is wired for {...} today; this dispatch is {harness}"}, None` (line
  733-736) — for grok this returns the declared-absent marker and `None`, so no
  `coordination-mcp.json` is ever written and no server argv is produced.
- `_mcp_argv()` (line 779): the `harness == "claude"` branch (783-787) wires only the lane MCP and
  ignores its own `coord` parameter entirely; the `harness == "codex"` branch (788-792) is the only
  one that calls `_codex_mcp_argv(COORD_MCP_SERVER, coord, COORD_MCP_ENV,
  capabilities=COORD_MCP_TOOLS)`; every other harness falls through to `return []` (line 794).
- `_grok_mcp_config()` (line 797-809) is grok's actual MCP-wiring path (grok reads
  `$GROK_HOME/config.toml`, not argv) and it writes exactly one block, keyed
  `[mcp_servers.{LANE_MCP_KEY}]` — the lane MCP. There is no grok-side equivalent call anywhere for
  the coordination/acting server; none exists to write.

This is the same gap the integration plan already names (§2, "Reuse and exact remaining gaps"):
"Launcher acting MCP | Assignment-bound worker identity and acting-MCP configuration are
implemented for **Codex** | Extend the existing per-harness projection for Claude and Grok; do
not assume all harnesses already receive acting tools." A-477 is that gap tripping in a live
dispatch: the grok launch path produces a worker with no acting-coordination tool and a brief
that never mentions the assignment it was minted for, so it can neither be told to claim nor able
to.

## Cause, one line

Grok's dispatch path never runs the acting-coordination-MCP projection at all
(`COORD_MCP_HARNESSES = ("codex",)`, `launch.py:639`, gating `_coordination_mcp()` and the codex-only
branch of `_mcp_argv()`) — so A-477's worker got no `coordination-mcp.json`, no `coord_claim` tool,
and a brief that never names its own assignment, while A-478's codex worker got all three; a
second, smaller, independent bug (the lane MCP's brief-vs-config server-name spelling,
`agentscient-lane` vs `agentscient_lane`) sits on top of it for grok specifically.

## Smallest fix (not applied)

Add `"grok"` to `COORD_MCP_HARNESSES` (launch.py:639) and give grok a coordination-server-wiring
path analogous to `_grok_mcp_config()` (launch.py:797) — write a second
`[mcp_servers.{COORD_MCP_KEY}]` block into `$GROK_HOME/config.toml` from the same `coord` server
